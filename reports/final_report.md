# Day 10 Reliability Report

## 1. Architecture Summary

The gateway implements a layered reliability strategy: every request first checks the cache (in-memory or Redis), then attempts each provider in order through its circuit breaker, and falls back to a static message only when all providers fail.

```
User Request
    |
    v
[ReliabilityGateway.complete()]
    |
    +---> [Cache.get(prompt)]
    |         |
    |         +-- HIT  --> return cached response (route: "cache_hit:<score>")
    |         |
    |         +-- MISS --> continue
    |
    +---> [CircuitBreaker: primary]
    |         |
    |         +-- OPEN      --> CircuitOpenError (fail fast, no retry storm)
    |         +-- HALF_OPEN --> allow one probe request
    |         +-- CLOSED    --> call primary provider
    |                              |
    |                              +-- success --> cache.set(), return (route: "primary:primary")
    |                              +-- failure --> record_failure(), continue
    |
    +---> [CircuitBreaker: backup]
    |         |
    |         +-- OPEN      --> CircuitOpenError (fail fast)
    |         +-- else      --> call backup provider
    |                              |
    |                              +-- success --> cache.set(), return (route: "fallback:backup")
    |                              +-- failure --> continue
    |
    +---> Static fallback message (route: "static_fallback")
```

## 2. Configuration

## 5. Cache Comparison

| Metric | Without cache | With cache | Delta |
|---|---:|---:|---|
| latency_p50_ms | 284.47 | 0.08 | -99.97% |
| latency_p95_ms | 526.92 | 320.57 | -39.2% |
| estimated_cost | 0.171776 | 0.036664 | -78.7% |
| estimated_cost_saved | 0.0 | 0.308 | +0.308 |
| cache_hit_rate | 0.0 | 0.7725 | +0.7725 |
| circuit_open_count | 25 | 6 | -76% |

**Key insight:** The cache absorbs 77% of repeated queries, reducing both cost by ~79% and circuit pressure by ~76%. The P50 latency drops to sub-millisecond because cache lookups cost ~0.08ms vs provider calls at ~280ms.

**False-hit guardrail example:**  
Query: `"Summarize refund policy for 2026 deadline"` — cached entry was `"refund policy for 2024 deadline"` with bigram similarity ~0.87. Without the `_looks_like_false_hit` guard, this would have returned stale 2024 data at threshold=0.3. With the guard, `{2026} ≠ {2024}` triggers rejection.

**Threshold justification:** 0.92 was chosen because at 0.85, the two date-variant queries (`2024` vs `2026`) had bigram similarity of ~0.87, causing false hits. At 0.92, only near-identical queries match, eliminating the false hit.

**TTL justification:** 300 seconds (5 minutes). Policy/FAQ queries are stable within a session. Shorter TTL (60s) would drop hit rate significantly; longer (3600s) risks serving stale answers if policy changes intra-hour.

## 6. Redis Shared Cache

**Why in-memory cache is insufficient for multi-instance deployments:**  
Each process has its own in-memory cache. If 3 gateway instances run behind a load balancer, a query cached by instance A is invisible to instances B and C, resulting in redundant API calls, inconsistent responses, and no real cost savings at scale.

**How `SharedRedisCache` solves this:**  
All instances connect to a single Redis server. Cache entries are keyed by `rl:cache:{md5_hash}` and shared atomically. TTL is managed by Redis EXPIRE, so no manual eviction is needed. Privacy-sensitive queries (matching `PRIVACY_PATTERNS`) and false-hit candidates are rejected before storage.

### Evidence of shared state

```
# Two separate SharedRedisCache instances reading the same data:

c1 = SharedRedisCache(redis_url="redis://localhost:6379/0", ttl_seconds=60,
                      similarity_threshold=0.5, prefix="rl:test:shared:")
c2 = SharedRedisCache(redis_url="redis://localhost:6379/0", ttl_seconds=60,
                      similarity_threshold=0.5, prefix="rl:test:shared:")

c1.set("shared query", "shared response")
cached, _ = c2.get("shared query")
assert cached == "shared response"   # PASSES — test_shared_state_across_instances
```

All 6 Redis tests pass: connection, set+get, TTL expiry, shared state, privacy bypass, false-hit detection.

### In-memory vs Redis latency comparison

| Metric | In-memory cache | Redis cache | Notes |
|---|---:|---:|---|
| latency_p50_ms | 0.08 | ~0.13 | Redis adds ~0.05ms network RTT to localhost |

Redis cache adds ~0.05ms overhead vs in-memory, which is negligible compared to provider latency (180–260ms). The tradeoff (shared state, horizontal scalability) is well worth it.

## 8. Failure Analysis

**Remaining weakness: Circuit state is per-process, not shared.**

When running multiple gateway instances, each has its own circuit breaker state. Instance A might have an OPEN circuit (protecting against a failing provider) while Instance B still has a CLOSED circuit and continues hammering the same failing provider — causing retry storms at the fleet level, not just the instance level.

**What would I change:**  
Store circuit breaker counters in Redis using atomic INCR/EXPIRE operations. When `failure_count:primary` key in Redis exceeds `failure_threshold`, all instances see the circuit as OPEN. This matches how production systems like Netflix Hystrix handle distributed circuit state.

**Secondary weakness:** The similarity scan in `SharedRedisCache.get()` is O(n) — it scans all cached keys. With thousands of entries this becomes slow. Fix: use a Redis sorted set or inverted index keyed by n-gram hashes to reduce lookups to O(k) where k is candidates matching at least one bigram.

## 9. Next Steps

1. **Redis-backed circuit state**: Move `failure_count` and `opened_at` to Redis (INCR + EXPIRE) so all gateway instances share circuit state, preventing fleet-level retry storms.

2. **Concurrent load testing**: Implement `concurrent.futures.ThreadPoolExecutor` in `run_simulation` using the `concurrency` config value. Current sequential execution underestimates real-world contention and cache stampede risk.

3. **SLO alerting**: Define Prometheus counters matching the slide metrics (`agent_requests_total`, `agent_latency_seconds`, `cache_hits_total`, `circuit_state`) and add a Grafana alert when availability drops below 99% for 60+ seconds.
